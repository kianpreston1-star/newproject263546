# Phase 6 — n8n as the control plane (weeks 17–19)

**Gate:** a `/halt` command from your phone stops live trading in under 5 seconds. Every
workflow is exported to git, credential-free, and CI-validated. Killing n8n entirely does not
stop trading, does not stop risk controls, and does not stop your pager.

---

## 6.1 What n8n is for, and what it must never do

n8n is the system's nervous system for everything that happens on human timescales. It is
not, and must never become, part of the trading decision path.

### ✅ n8n owns
Research ingestion · alerting and escalation · human-in-the-loop approvals · reporting ·
deployment and promotion workflows · retraining triggers · ops runbooks and self-healing ·
calendar-driven blackout windows · venue status monitoring · trade journaling · compliance
and audit trails · tax/accounting exports · capital ramp proposals · cost monitoring

### ❌ n8n must never
Compute a trading signal · size a position · place, modify or cancel an order directly at a
venue · hold an exchange API key · sit between the feedhandler and the strategy · be a
dependency of any risk control · be in the path of a critical page

> **The load-bearing rule: safety asymmetry.** n8n may *always* make the system safer
> without asking anyone — halt, flatten, de-risk, reduce limits, blacklist an instrument.
> It may *never* make the system riskier without a cryptographically signed human approval —
> resume, raise limits, increase size, deploy a strategy, whitelist an instrument.
>
> Enforce this in the control API's authorization layer, not in workflow logic. Workflow JSON
> is easy to edit by accident; a server-side policy is not.

## 6.2 Deploying n8n properly (queue mode)

The default single-container n8n is a toy. Queue mode gives you horizontal workers, survives
a worker crash mid-execution, and separates webhook ingestion from execution — which is what
you need when a workflow failure must not swallow an alert.

`docker-compose.n8n.yml` — deliberately a separate file so you can restart the control plane
without touching the trading stack.

```yaml
name: kairos-control

x-n8n-common: &n8n-common
  image: n8nio/n8n:latest
  environment: &n8n-env
    # --- state ---
    DB_TYPE: postgresdb
    DB_POSTGRESDB_HOST: postgres
    DB_POSTGRESDB_DATABASE: n8n
    DB_POSTGRESDB_USER: n8n
    DB_POSTGRESDB_PASSWORD: ${N8N_DB_PASSWORD}
    DB_POSTGRESDB_POOL_SIZE: "10"

    # --- queue mode: the whole point ---
    EXECUTIONS_MODE: queue
    QUEUE_BULL_REDIS_HOST: redis
    QUEUE_BULL_REDIS_PORT: "6379"
    QUEUE_BULL_REDIS_PASSWORD: ${REDIS_PASSWORD}
    QUEUE_BULL_REDIS_DB: "2"               # keep off the trading cache's DB
    QUEUE_HEALTH_CHECK_ACTIVE: "true"

    # --- credentials encryption. LOSE THIS KEY AND EVERY CREDENTIAL IS UNRECOVERABLE. ---
    N8N_ENCRYPTION_KEY: ${N8N_ENCRYPTION_KEY}

    # --- hygiene: an unpruned n8n DB will grow to hundreds of GB ---
    EXECUTIONS_DATA_PRUNE: "true"
    EXECUTIONS_DATA_MAX_AGE: "336"          # hours (14 days)
    EXECUTIONS_DATA_PRUNE_MAX_COUNT: "50000"
    EXECUTIONS_DATA_SAVE_ON_SUCCESS: "all"  # you want the audit trail
    EXECUTIONS_DATA_SAVE_ON_ERROR: "all"

    # --- hardening ---
    N8N_BLOCK_ENV_ACCESS_IN_NODE: "true"    # Code nodes cannot read process.env
    N8N_RUNNERS_ENABLED: "true"             # Code nodes in an isolated task runner
    N8N_DIAGNOSTICS_ENABLED: "false"
    N8N_VERSION_NOTIFICATIONS_ENABLED: "false"
    N8N_PERSONALIZATION_ENABLED: "false"
    N8N_HIRING_BANNER_ENABLED: "false"
    N8N_PAYLOAD_SIZE_MAX: "16"              # MB
    N8N_SECURE_COOKIE: "true"
    N8N_PROXY_HOPS: "1"                     # behind the reverse proxy

    # --- observability ---
    N8N_METRICS: "true"                     # /metrics for Prometheus
    N8N_METRICS_INCLUDE_WORKFLOW_ID_LABEL: "true"
    N8N_LOG_LEVEL: info
    N8N_LOG_OUTPUT: console                 # JSON to stdout -> Loki

    # --- time: every cron in this system is UTC. no exceptions, no DST bugs. ---
    GENERIC_TIMEZONE: UTC
    TZ: UTC

  n8n-main:                                 # UI + scheduler. NOT webhooks, NOT executions.
    <<: *n8n-common
    environment:
      <<: *n8n-env
      N8N_HOST: ${N8N_HOST}
      N8N_PROTOCOL: https
      WEBHOOK_URL: https://${N8N_HOST}/
      N8N_DISABLE_PRODUCTION_MAIN_PROCESS: "true"   # offload webhooks to the webhook svc
    ports: ["5678:5678"]
    volumes: [n8ndata:/home/node/.n8n]
    depends_on: [postgres, redis]

  n8n-webhook:                              # ingestion only; scales independently
    <<: *n8n-common
    command: webhook
    environment:
      <<: *n8n-env
      WEBHOOK_URL: https://${N8N_HOST}/
    deploy: { replicas: 2 }
    depends_on: [postgres, redis]

  n8n-worker:                               # all executions happen here
    <<: *n8n-common
    command: worker --concurrency=10
    environment:
      <<: *n8n-env
      N8N_CONCURRENCY_PRODUCTION_LIMIT: "10"
    deploy: { replicas: 2 }
    depends_on: [postgres, redis]

volumes:
  n8ndata: {}
```

Put it behind Caddy or Traefik with TLS, and bind the UI to a VPN/Tailscale interface only.
**The n8n UI must never be reachable from the public internet.** It is, by design, a remote
code execution surface for whoever can log in. Add SSO/2FA if your edition supports it.

Back up two things, separately, and test the restore: the `n8n` Postgres database, and
`N8N_ENCRYPTION_KEY`. Losing the key means re-entering every credential by hand.

## 6.3 The security model

```
┌──────────┐  signed webhook   ┌──────────────┐  scoped JWT   ┌─────────────┐
│ external │ ───(HMAC-SHA256)─▶│     n8n      │ ─────────────▶│ control-api │
│ sources  │  + timestamp      │              │  + idempotency│             │
└──────────┘  + nonce          └──────────────┘  key          └──────┬──────┘
                                      ▲                              │ audited,
                                      │ approval callback            │ policy-checked
                                 ┌────┴─────┐                        ▼
                                 │  you,    │                 ┌─────────────┐
                                 │ on phone │                 │ risk engine │
                                 └──────────┘                 │     OMS     │
                                                              └─────────────┘
                                                        exchange keys live ONLY here
```

### Inbound to n8n: verify every webhook

Any public webhook endpoint will be found and probed. Each one starts with a Code node doing
constant-time HMAC verification plus replay protection:

```javascript
// n8n Code node — "Verify HMAC" — first node of EVERY public webhook workflow
const crypto = require('crypto');

const sig   = $input.first().json.headers['x-kairos-signature'];
const ts    = $input.first().json.headers['x-kairos-timestamp'];
const nonce = $input.first().json.headers['x-kairos-nonce'];
const body  = JSON.stringify($input.first().json.body);

// 1. Freshness: reject anything older than 5 minutes, so a captured request
//    cannot be replayed tomorrow.
if (Math.abs(Date.now() / 1000 - Number(ts)) > 300) {
  throw new Error('stale timestamp');
}

// 2. Signature over timestamp + nonce + body, so none of them can be swapped.
const expected = crypto
  .createHmac('sha256', $env.KAIROS_WEBHOOK_SECRET)
  .update(`${ts}.${nonce}.${body}`)
  .digest('hex');

// 3. Constant-time compare. A plain === leaks the signature through timing.
const a = Buffer.from(sig || '', 'hex');
const b = Buffer.from(expected, 'hex');
if (a.length !== b.length || !crypto.timingSafeEqual(a, b)) {
  throw new Error('bad signature');
}

// 4. Replay: the nonce must be unused. Checked against Redis in the next node,
//    with SET NX EX 600 -- if the key already existed, this is a replay.
return [{ json: { ...$input.first().json.body, _nonce: nonce } }];
```

`N8N_BLOCK_ENV_ACCESS_IN_NODE: "true"` blocks `$env` in Code nodes, so pass the secret in
through the workflow's credential store instead, or set
`N8N_BLOCK_ENV_ACCESS_IN_NODE: "false"` *only* if you accept that any Code node can then read
every environment variable in the container. The credential-store route is correct.

### Outbound from n8n: the control API enforces policy

n8n holds one credential: a JWT for `control-api`, scoped by claim, rotated weekly.

```python
# services/control-api/policy.py
SAFE_ENDPOINTS = {            # n8n may call these unilaterally, any time
    "POST /v1/halt",                      # stop opening new positions
    "POST /v1/flatten",                   # close everything
    "POST /v1/derisk",                    # scale all sizes down by a factor
    "POST /v1/blacklist-instrument",
    "POST /v1/reduce-limits",
    "POST /v1/blackout-window",           # e.g. around an FOMC release
    "GET  /v1/*",                         # all reads
}

RISK_INCREASING_ENDPOINTS = {  # require a valid, unexpired, signed human approval
    "POST /v1/resume",
    "POST /v1/raise-limits",
    "POST /v1/whitelist-instrument",
    "POST /v1/deploy-strategy",
    "POST /v1/set-capital-allocation",
    "POST /v1/override-risk-rule",        # two-person rule, below
}

TWO_PERSON = {"POST /v1/override-risk-rule", "POST /v1/set-capital-allocation"}

async def authorize(req: Request) -> None:
    route = f"{req.method} {req.url.path}"
    claims = verify_jwt(req.headers["authorization"], audience="control-api")

    if match(route, SAFE_ENDPOINTS):
        return await audit(route, claims, approval=None)

    if not match(route, RISK_INCREASING_ENDPOINTS):
        raise HTTPException(403, "endpoint not reachable from the control plane")

    token = req.headers.get("x-kairos-approval")
    if not token:
        raise HTTPException(403, "human approval required")

    approval = verify_approval_token(
        token,
        expected_action=route,
        expected_payload_hash=sha256_canonical(await req.json()),   # bind to THIS payload
        max_age_s=600,
    )
    if route in TWO_PERSON and len(approval.approvers) < 2:
        raise HTTPException(403, "two approvers required")
    if approval.nonce_already_used():          # single-use
        raise HTTPException(403, "approval already consumed")

    await audit(route, claims, approval=approval)
```

Four properties make the approval token safe, and all four matter:

1. **Bound to the exact payload** (hash in the token) — you cannot approve "resume with 1%
   size" and have it used for "resume with 100% size".
2. **Short-lived** (10 minutes) — an approval screenshot from last week is worthless.
3. **Single-use** (nonce consumed server-side) — no replay.
4. **Signed by a key n8n does not hold** — your approval key lives on your phone/laptop, so a
   fully compromised n8n still cannot increase risk.

### Idempotency

Every mutating call from n8n carries `Idempotency-Key: <uuid>`. The control API stores the
key with its response for 24 hours and returns the cached response on repeat. n8n *will*
retry — on timeouts, on worker restarts, on your accidental double-click — and without this,
a retried "flatten" is harmless but a retried "raise limits" is not.

## 6.4 The workflow catalogue

24 workflows, grouped. Each lists trigger → steps → failure mode. Build them in the order
given; the first four are the ones that earn their keep immediately.

### Group A — safety and alerting (build first)

**A1 · `wf-kill-switch`** — *the one you test weekly*
- **Trigger:** Telegram/Slack command `/halt`, or a web form
- **Steps:** verify sender ID against an allowlist (not the display name — IDs) → optional
  2FA code → `POST /v1/halt` with idempotency key → poll `GET /v1/status` until `halted` →
  reply with confirmation and current positions
- **Must complete in under 5 seconds.** Measure it. Alert if it regresses.
- **Failure mode:** if the control API is unreachable, reply with the manual runbook link and
  the exchange's own web-UI cancel-all URL. Never fail silently.

**A2 · `wf-alert-router`**
- **Trigger:** Alertmanager webhook
- **Steps:** verify HMAC → dedupe on fingerprint (Redis, 5 min) → Switch on severity →
  `critical`: page via phone call (Twilio) + Telegram + create an incident record;
  `warning`: Telegram; `info`: log only → attach Grafana panel snapshot and the runbook link
- **Failure mode:** Alertmanager *also* routes critical alerts directly to your phone,
  bypassing n8n entirely. Your paging path must not depend on your workflow engine.

**A3 · `wf-venue-health`**
- **Trigger:** schedule, every 60s
- **Steps:** fetch each venue's status page/API + your own measured reject rate and ack
  latency → if degraded: `POST /v1/derisk {venue, factor: 0.5}`; if down:
  `POST /v1/halt {venue}` → notify
- This is pure safety-direction, so it needs no approval — exactly what the asymmetry is for.

**A4 · `wf-recon-break`**
- **Trigger:** event bus `alerts.critical` (reconciliation break)
- **Steps:** snapshot internal + venue state to S3 → page immediately → post a side-by-side
  diff to Telegram → offer two buttons: *Flatten everything* (safe, no approval) and
  *Accept venue state as truth* (risk-increasing → requires signed approval)
- **Never auto-correct.** A bug that invented a position will cheerfully "correct" you into a
  real one.

### Group B — human-in-the-loop gates

**B1 · `wf-approval-gate`** — a reusable sub-workflow called by every risk-increasing flow
- **Trigger:** Execute Workflow (called by others)
- **Steps:** render a decision card (what, why, current exposure, what changes, the
  payload hash) → Telegram with inline buttons → **Wait node in `webhook` resume mode** →
  on click, verify the approver's ID and signature → mint the approval token → return it
- **Timeout:** 15 minutes → denied by default. **Default-deny on timeout is the point.**

**B2 · `wf-strategy-promotion`**
- **Trigger:** manual, or `wf-model-retrain` finding a better champion
- **Steps:** run the full validation suite (CPCV, DSR, PBO) → compare to the incumbent →
  render a scorecard → `wf-approval-gate` → on approve, `POST /v1/deploy-strategy` in
  **shadow** mode only → schedule a 7-day review follow-up
- Promotion through shadow → paper → 1% → 10% → 100% always requires a fresh approval at each
  step. No single click ever goes from backtest to full size.

**B3 · `wf-capital-ramp`**
- **Trigger:** schedule, weekly (Monday 08:00 UTC)
- **Steps:** evaluate the Phase 10 ramp criteria → if all pass, propose the next size tier →
  `wf-approval-gate` → `POST /v1/set-capital-allocation` (two-person)
- **Failure mode:** criteria not met → post *why not*, which is the more useful message.

**B4 · `wf-param-change-audit`**
- **Trigger:** webhook from the control API on any config change
- **Steps:** diff old vs. new → classify risk-increasing or not → append to the audit table →
  notify → if risk-increasing *and* it somehow arrived without an approval token, **page**
  (that means the policy layer was bypassed, which is a security incident)

### Group C — data and research ingestion

**C1 · `wf-news-ingest`**
- **Trigger:** RSS/webhook (Benzinga, venue announcements, EDGAR full-text, CoinDesk)
- **Steps:** dedupe on URL hash → extract text → **Claude structured extraction** (Phase 8) →
  write to `research.news_events` with `ts_available = now()` (never the publish timestamp) →
  publish to the event bus → if `severity >= high`, `POST /v1/blackout-window`
- **Failure mode:** LLM failure → store the raw text with `classification = null` and retry
  later. Never block ingestion on classification.

**C2 · `wf-macro-calendar`**
- **Trigger:** schedule, daily 00:17 UTC
- **Steps:** fetch the week's economic calendar (FRED + a calendar API) → for each high-impact
  release, `POST /v1/blackout-window {from: T-5m, to: T+15m, scope: all}`
- Mechanically avoids the worst slippage and stop-hunting windows in the week. One of the
  highest value-per-line-of-code workflows in the whole catalogue.

**C3 · `wf-earnings-blackout`** (equities) — same shape, from the earnings calendar, blacking
out the session before through the session after.

**C4 · `wf-funding-scan`** (crypto perps)
- **Trigger:** schedule, every 15 minutes
- **Steps:** pull funding rates across venues → compute the cross-venue spread → if a
  configured threshold is crossed, publish a `basis_opportunity` event for the strategy
  engine to *consider*
- Note the boundary: n8n publishes an **observation**, not a trade. The strategy decides.

**C5 · `wf-data-quality`**
- **Trigger:** event bus `data.quality.failed`
- **Steps:** classify the failure → attempt automated backfill from REST history → re-run the
  check → if fixed, log and notify quietly; if not, `POST /v1/blacklist-instrument` and page
- Self-healing for the 90% of gaps that are a venue hiccup, escalation for the rest.

**C6 · `wf-sentiment-sweep`**
- **Trigger:** schedule, hourly
- **Steps:** collect from configured sources → **Claude batch classification** (Phase 8) → aggregate to
  a per-instrument score → write to the feature store with an explicit `ts_available`
- **Hard cap:** this feature's contribution to position size is bounded in config (Phase 8).
  Social sentiment is trivially manipulable; treat it as a tiebreaker at most.

### Group D — reporting and journaling

**D1 · `wf-daily-report`**
- **Trigger:** schedule, 23:47 UTC (jittered off the hour deliberately — everyone's cron
  fires at :00 and APIs throttle)
- **Steps:** query PnL, attribution, TCA, risk metrics, veto counts → render charts →
  build a PDF/HTML → email + Telegram + archive to S3
- Sections: equity and drawdown · PnL by strategy and instrument · attribution (price,
  funding, fees, slippage) · execution quality with markouts · risk vetoes by rule · data
  quality incidents · live-vs-backtest divergence · open positions and risk metrics

**D2 · `wf-weekly-review`**
- **Trigger:** schedule, Sunday 18:00 UTC
- **Steps:** aggregate the week → pull the 10 worst trades with full market context →
  **Claude postmortem** (Phase 8) → regime analysis → strategy decay check (rolling Sharpe
  vs. backtest) → produce a review doc with explicit recommendations
- **The LLM proposes; it never deploys.** Recommendations land as a document and, where
  actionable, a draft pull request.

**D3 · `wf-trade-journal`**
- **Trigger:** event bus, on each closed position
- **Steps:** enrich with entry/exit context, the signal values at the time, concurrent news,
  the realized TCA → append to Postgres and Notion
- This dataset is how you later answer "which setups actually work?" with data instead of
  recollection.

**D4 · `wf-monthly-accounting`**
- **Trigger:** schedule, 1st of the month
- **Steps:** export all fills → compute realized PnL with the right lot method → generate
  tax-lot CSV → push to accounting software → archive immutably to S3 with object-lock

**D5 · `wf-cost-watch`**
- **Trigger:** schedule, daily
- **Steps:** sum LLM spend, infra spend, data subscriptions, exchange fees → compare to the
  configured budget and to gross PnL → alert if costs exceed a set fraction of PnL
- The workflow that notices you are paying $300/month to earn $150.

### Group E — ops and lifecycle

**E1 · `wf-model-retrain`**
- **Trigger:** schedule, weekly, *and* on a feature-drift alert
- **Steps:** trigger the Dagster training job → wait for completion → run the full validation
  suite → compare to the champion on out-of-sample → if better by a material margin, open a
  GitHub PR with the scorecard and call `wf-strategy-promotion`
- **Never auto-promotes.** A weekly auto-retrain that auto-deploys is a machine for
  overfitting to last week.

**E2 · `wf-deploy`**
- **Trigger:** GitHub webhook on merge to `main`
- **Steps:** verify CI green including chaos tests → build and push the image → **check that
  current drawdown < 2% and no position is open above a threshold** (never deploy into a
  drawdown) → rolling restart → verify health → smoke test → announce
- **Rollback:** if error rate or drawdown rises within 1 hour of deploy, auto-rollback and page.

**E3 · `wf-incident`**
- **Trigger:** called by `wf-alert-router` on critical
- **Steps:** create an incident record → post a dedicated channel/thread → attach the runbook →
  track acknowledgement → escalate if unacked in 5 minutes → on resolution, prompt for a
  postmortem and file it

**E4 · `wf-backup-verify`**
- **Trigger:** schedule, weekly
- **Steps:** take a fresh backup → **restore it into a scratch environment** → run integrity
  checks → report
- An unverified backup is not a backup. This workflow is how you find out the restore is
  broken on a Tuesday rather than during an incident.

**E5 · `wf-key-rotation`**
- **Trigger:** schedule, monthly, and on an expiry alert
- **Steps:** check exchange key age, TLS cert expiry, JWT signing key age → rotate what can
  be rotated automatically → create tasks for the rest → verify the new credential works
  *before* revoking the old one

**E6 · `wf-dependency-audit`**
- **Trigger:** schedule, weekly
- **Steps:** `pip-audit` / `npm audit` / Trivy on images → triage by severity → open PRs for
  patches → page on anything critical and reachable

**E7 · `wf-regime-brief`**
- **Trigger:** schedule, 06:00 UTC daily
- **Steps:** gather overnight moves, vol regime, funding, OI changes, the day's calendar →
  **Claude** (Phase 8) writes a one-page brief → Telegram
- Informational. It does not touch position sizing.

**E8 · `wf-error-handler`** — set as `N8N_DEFAULT_ERROR_WORKFLOW`
- **Trigger:** Error Trigger (fires when any other workflow fails)
- **Steps:** capture the workflow, node, error and input → dedupe → notify → if the failed
  workflow was tagged `safety-critical`, **page**
- Without this, a failing workflow fails *silently*, and you discover three weeks later that
  your macro-blackout automation has been dead the whole time. Set it on day one.

## 6.5 Workflows as code

A workflow that exists only in n8n's database is an undocumented, unreviewed, unbackupable
part of your trading system. Treat them like code.

```bash
# Export (run in the n8n container, or via CLI against the same DB)
n8n export:workflow --all --separate --output=/export/workflows
n8n export:credentials --all --output=/export/creds.json      # ENCRYPTED. never --decrypted.

# Strip volatile/sensitive fields before committing
python scripts/sanitize_n8n.py /export/workflows n8n/workflows/

# Import on deploy
n8n import:workflow --separate --input=/import/workflows
```

`scripts/sanitize_n8n.py` removes `id`, `versionId`, `createdAt`, `updatedAt`, `meta`,
`pinData` and any inline credential blob, then sorts keys so diffs are readable. Without it,
every export produces a 400-line diff of nothing.

`scripts/validate_n8n_workflows.py` runs in CI and **fails the build** on:

```python
RULES = [
    "no node contains a string matching a secret pattern (API key, private key, JWT)",
    "every workflow has an errorWorkflow configured",
    "every HTTP Request node's host is in the allowlist",
    "every publicly-exposed Webhook node's first node verifies HMAC",
    "no workflow calls a venue API host directly",       # <- the two-loop rule, enforced
    "every workflow that calls a RISK_INCREASING endpoint invokes wf-approval-gate",
    "every Schedule Trigger uses a non-zero minute",     # cron jitter
    "every workflow has an owner tag and a description",
    "no Code node uses require() outside the allowlist",
]
```

That fourth-from-last rule is the important one: it mechanically prevents someone (including
future you, at 2am) from adding a direct exchange call inside n8n and quietly putting the
control plane in the hot path.

## 6.6 Custom n8n node for the control API

Rather than 24 hand-rolled HTTP Request nodes with copy-pasted auth, write one declarative
node. It centralizes auth, idempotency keys, and approval-token plumbing, so none of those can
be forgotten in a workflow.

```typescript
// n8n/nodes/Kairos/Kairos.node.ts
import type { INodeType, INodeTypeDescription } from 'n8n-workflow';

export class Kairos implements INodeType {
  description: INodeTypeDescription = {
    displayName: 'Kairos Control',
    name: 'kairos',
    group: ['transform'],
    version: 1,
    description: 'Talks to the Kairos control API. Safe ops are direct; risk-increasing ops require an approval token.',
    defaults: { name: 'Kairos' },
    inputs: ['main'],
    outputs: ['main'],
    credentials: [{ name: 'kairosApi', required: true }],
    requestDefaults: {
      baseURL: '={{$credentials.baseUrl}}',
      headers: { 'Content-Type': 'application/json' },
    },
    properties: [
      {
        displayName: 'Operation',
        name: 'operation',
        type: 'options',
        default: 'status',
        options: [
          // --- safe: no approval needed ---
          { name: 'Get Status',   value: 'status',   action: 'Read system status' },
          { name: 'Halt',         value: 'halt',     action: 'Stop opening positions' },
          { name: 'Flatten',      value: 'flatten',  action: 'Close all positions' },
          { name: 'De-risk',      value: 'derisk',   action: 'Scale sizes down' },
          { name: 'Blackout',     value: 'blackout', action: 'Add a no-trade window' },
          // --- risk-increasing: approval token REQUIRED ---
          { name: 'Resume',       value: 'resume',   action: 'Resume trading' },
          { name: 'Raise Limits', value: 'raise',    action: 'Increase risk limits' },
          { name: 'Deploy',       value: 'deploy',   action: 'Deploy a strategy' },
        ],
      },
      {
        displayName: 'Approval Token',
        name: 'approvalToken',
        type: 'string',
        typeOptions: { password: true },
        default: '',
        description: 'From wf-approval-gate. Required for risk-increasing operations.',
        displayOptions: { show: { operation: ['resume', 'raise', 'deploy'] } },
        routing: { send: { type: 'header', property: 'X-Kairos-Approval' } },
      },
    ],
  };
}
```

Pair it with a `KairosApi` credential type holding the base URL and JWT, and generate the
`Idempotency-Key` header in the node's `preSend` hook so no workflow can omit it.

## 6.7 Monitoring n8n itself

Scrape `n8n-main:5678/metrics` into Prometheus and alert on:

| Alert | Why it matters |
|---|---|
| `wf-kill-switch` has not succeeded in 7 days | Your emergency stop is untested. Fire a weekly synthetic test and alert on *that*. |
| Any `safety-critical` workflow failed | Silent safety automation is worse than none |
| Queue depth > 100 for 5 min | Workers are wedged; alerts are being delayed |
| Worker count < 1 | Nothing is executing at all |
| Execution duration p95 up 3× week-on-week | Something is degrading |
| `wf-macro-calendar` found 0 events on a weekday | Almost certainly a broken API, not a quiet week |
| n8n DB size > 20 GB | Pruning is misconfigured |

That last-but-one pattern generalizes: **alert on a workflow producing suspiciously empty
results**, not just on it erroring. The most dangerous automation failure is the one that
succeeds and does nothing.

compose -f docker-compose.n8n.yml down` leaves trading and risk fully operational, and a
critical alert still reaches your phone. CI rejects a workflow with an embedded key. Every
